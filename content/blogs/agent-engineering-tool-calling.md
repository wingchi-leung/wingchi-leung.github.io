开发过 AI Agent 的工程师可能都有过类似的经历。

最开始，我们只是想让大模型能够调用几个工具，例如搜索商品、查询库存、创建订单。代码非常简单：

``` python 
async def execute_tool(call):
    if call.name == "search_product":
        return await search_product(call.arguments)
    elif call.name == "check_inventory":
        return await check_inventory(call.arguments)
    elif call.name == "create_order":
        return await create_order(call.arguments)
```

但随着产品不断迭代，我们开始遇到各种问题：

- 模型生成的参数不合法怎么办？
- 模型一直搜索商品，如何避免无限消耗 Token 和 API 费用？
- 用户没有订单权限，如何阻止工具执行？
- 一次返回多个 Tool Call，应该并行还是串行？
- 模型重复创建订单，如何避免产生多个订单？
- 工具执行失败了，如何让模型知道发生了什么？
- 工具执行结果需要同时交给模型、前端和日志系统，如何处理？
    
我们不断增加 `if-else`、`try-except` 和各种状态变量。最后，一个 `execute_tool_batch()` 可能膨胀到三四百行。

问题并不只是代码太长，而是**输入校验、预算、权限、执行调度、错误处理、状态管理等多个独立问题，全被塞进了一个函数。**

这篇文章以电商购物 Agent 为例，梳理 Tool Calling 中常见的工程问题，并看看 LangGraph、pi-agent、Vercel AI SDK 和 OpenAI Agents SDK 这些框架如何处理它们。

## 一、一个臃肿的 Tool Executor 是如何形成的？

假设用户告诉 Agent：

> 帮我找一双 42 码、500 元以内的黑色跑鞋，有货的话帮我下单。

Agent 需要完成三个任务：

1. `search_product`：搜索符合要求的商品。
2. `check_inventory`：查询库存。
3. `create_order`：创建订单。
    
模型可能分多轮调用工具，也可能一次返回多个 Tool Call。

最初我们只需要解析参数、执行函数、返回结果。

后来为了满足业务需求，逐渐加入了更多逻辑：

```
async def execute_tool_batch(calls, context):
    for call in calls:
        # 参数校验
        # 工具是否存在
        # 搜索预算检查
        # 用户权限检查
        # 当前店铺上下文校验
        # 重复调用检查
        # 串行或并行调度
        # 超时和异常处理
        # 更新订单状态
        # 发送前端事件
        # 汇总模型消息与审计日志
        ...
```

看起来每个逻辑都有必要，但它们其实属于完全不同的工程问题。

## 二、Tool Calling 的八个正交问题

所谓正交，就是这些问题的职责相互独立。修改预算策略，不应该影响权限校验；改变并发方式，也不应该影响工具向模型返回结果的格式。

|问题|电商场景|常见处理机制|
|---|---|---|
|输入合法性|商品数量传入字符串|Schema Validation|
|预算与循环控制|模型反复搜索商品|Budget / Step Limit|
|上下文与权限|用户操作其他店铺订单|Guard / Policy|
|执行调度|查询商品与创建订单如何协调|Tool Executor / Scheduler|
|去重与幂等|重复创建同一订单|Cache / Idempotency Key|
|错误处理|库存接口超时、参数错误|Error Contract / Retry|
|状态管理|下单后更新订单状态|State / Reducer|
|结果分发|返回模型、前端及审计系统|Events / Streaming / Tracing|

一个复杂的 Tool Executor，往往就是这八类逻辑逐渐耦合的结果。

### 1. 输入合法性：模型输出不能直接执行

LLM 可能生成错误的 JSON、缺少参数，甚至调用不存在的工具。

因此，工具执行前通常需要校验工具名称、参数结构和字段类型。

主流框架一般采用 Schema 驱动的工具定义。开发者声明参数结构，运行时负责解析与校验。

例如 LangChain 使用工具 Schema，Pydantic AI 使用 Pydantic 类型体系，Vercel AI SDK 常使用 Zod，pi-agent 则采用 TypeBox 风格的工具 Schema。

需要注意，**参数格式合法不代表业务上允许执行**。`quantity=2` 是合法整数，但用户是否有权购买，仍然是另一个问题。

### 2. 预算与循环控制：模型为什么停不下来？

假设模型一直搜索跑鞋：

第一次搜索黑色跑鞋，第二次搜索运动鞋，第三次搜索男士运动鞋……

每一次调用看起来都合理，但新增信息越来越少，API 成本却不断增加。

通常存在两层控制：

- **Agent 级限制**：限制模型最多运行多少轮、执行多长时间。
- **工具级限制**：限制某类工具的调用次数、费用或资源消耗。
    
例如，Vercel AI SDK 可以通过 `stopWhen` 限制 Agent Loop 的运行步数；OpenAI Agents SDK 也提供 `maxTurns`。

但是，“已经找到足够多的跑鞋，不应该继续搜索”属于业务上的搜索饱和判断，并不是通用框架天然能够理解的。

这也是为什么框架通常只解决通用预算机制，而业务系统还需要自己的停止条件。

### 3. 上下文与权限：能调用，不代表应该调用

假设一个电商 Agent 同时连接了多家店铺。

用户当前正在处理 A 店铺的订单，但模型生成的工具参数却包含 B 店铺的 `store_id`。

即使工具参数完全合法，也不能允许它直接操作。

这一问题可以分为两类：

**权限正确性**：用户是否有权操作资源？
**上下文正确性**：当前操作的资源是否属于正确的店铺、用户或会话？

常见处理方式是在工具执行前设置 Guard、Policy 或 Middleware。对于高风险操作，还可以增加 Human-in-the-loop，让用户明确批准。

但最终的租户隔离、数据库权限和资源归属校验，仍然必须由业务后端强制执行，不能只依赖模型或 Prompt。

### 4. 执行调度：串行还是并行？

假设模型一次生成三个工具调用：

```
search_product("黑色跑鞋")
get_coupon("运动鞋")
create_order("SKU-1001")
```

搜索商品和查询优惠券可能互不依赖，可以并行执行。

但创建订单涉及真实的外部写操作，还可能依赖前两个工具的结果。

因此，工具执行器需要区分并发调用、依赖关系和具有副作用的操作。

值得注意的是，**只把创建订单设置为串行，并不自动保证业务正确性**。

如果模型没有先确认库存，或者两次 Agent 运行同时创建相同订单，单个批次内的串行执行也无法解决这些问题。

### 5. 去重与幂等：重复调用不一定是同一个问题

这是 Agent 系统非常容易混淆的概念。

模型连续两次搜索相同商品，可以考虑使用缓存，避免重复请求。

但连续两次创建相同订单，不能简单靠缓存解决。

缓存解决的是重复计算；幂等解决的是重复操作的副作用。

尤其是下单请求超时的时候：

订单可能已经成功创建，只是网络断开，Agent 没收到响应。如果直接重试，就可能创建第二个订单。

因此，具有副作用的工具通常需要由后端提供稳定的幂等键、唯一约束或操作状态查询机制。

这类业务幂等性不是 Agent 框架能够自动保证的。

### 6. 错误处理：让模型知道下一步该怎么办

工具调用失败时，最简单的写法是：

```
except Exception:
    return {"error": "Tool failed"}
```

但对于模型来说，这样的信息几乎没有帮助。

我们需要区分：

- **参数错误**：模型可以修改参数后重新调用。
- **权限拒绝**：不能原样重试，可能需要用户授权。
- **上游限流**：可以等待或采用其他策略。
- **业务冲突**：例如库存不足，应重新选商品。
- **未知异常**：不应该默认无限重试。
    

常见的做法，是把底层错误映射成安全、结构化的工具错误结果，包含错误类型、是否建议重试、可执行的下一步。

例如：

``` python 
{
  "error_code": "out_of_stock",
  "retryable": false,
  "suggested_action": "请选择其他商品"
}
```

这里的 `retryable` 是业务建议，而不是 Agent 可以无条件自动重试的许可。尤其是下单这种有副作用的工具，超时后应先确认执行结果。

同时，也不应该把原始异常堆栈、Token 或数据库连接信息直接发给模型。

### 7. 状态管理：一次工具执行会改变什么？

创建订单之后，系统可能需要更新：

- 当前订单 ID
- 用户是否已经完成确认
- 订单创建状态
- 当前 Agent 的任务进度
    
如果工具执行器通过大量共享变量维护这些状态，那么串行、并行和异常恢复都可能产生问题。

现代 Agent 框架通常会把会话状态与工具执行分开管理。

典型代表是 LangGraph 的 State 和 Reducer：工具或节点产生状态更新，由图运行时按约定合并。

但 Reducer 只解决状态更新的组织方式，不等于数据库事务，也不保证外部订单系统的状态一致性。

### 8. 结果分发：为什么一个 Tool Result 会越来越复杂？

同一个工具执行结果，可能需要交给不同消费者。

例如，成功创建订单之后：

- LLM 需要知道订单已经创建。
- 前端需要显示订单卡片。
- 日志系统需要记录耗时、错误和调用信息。
- 审计系统需要记录操作发生的时间和授权依据。
    
如果在工具执行函数内部同时拼接模型消息、前端事件和审计对象，就会产生大量结果类型判断。

主流框架倾向于通过运行事件、状态、流式消息和追踪机制，把这些消费者分离。

但 UI 订单卡片与审计记录仍然需要由应用定义数据结构和持久化逻辑。

## 三、主流 Agent 框架是怎么处理这些问题的？

理解问题之后，我们再来看几个具有代表性的框架。

它们的共同点是尽量不让开发者反复编写基础 Tool Calling Loop，但具体设计哲学并不相同。

### 1. LangGraph / LangChain：通过 Middleware、ToolNode 和 State 分离职责

LangChain 更偏向提供开箱即用的 Agent 抽象；LangGraph 则提供更底层的状态图和执行控制。

LangGraph 中一个重要组件是 `ToolNode`。

它负责执行模型生成的工具调用，管理工具消息、并发执行和错误处理，同时支持向工具注入状态与运行时上下文。

对于我们讨论的问题，LangChain / LangGraph 的思路可以概括为：

| 问题     | 典型机制                             |
| ------ | -------------------------------- |
| 参数校验   | Tool Schema                      |
| 预算与循环  | Middleware、模型调用限制、图路由            |
| 权限与上下文 | Middleware、Runtime Context、工具校验  |
| 执行调度   | ToolNode、Send、Graph Dependencies |
| 错误处理   | ToolNode 错误处理、RetryPolicy        |
| 状态管理   | State、Reducer、Checkpoint         |
| 结果分发   | ToolMessage、State Update、Stream  |

其中最有代表性的是 **State Reducer**。

它允许开发者声明不同字段应该如何合并。例如消息追加到历史记录，某些状态字段则使用最新值。

这避免了所有工具都直接修改同一批全局变量。

另外，通过 Checkpointer 与 `interrupt()`，LangGraph 可以在需要用户批准时暂停工作流，并在提供恢复输入后继续执行。

**LangGraph 的优势是控制流程清晰，适合状态复杂、需要恢复和人工审批的 Agent。**

代价是开发者需要理解 Graph、Node、State、Reducer 以及持久化等概念。对于只有几个工具的简单 Agent，未必需要这么多抽象。

### 2. pi-agent：保持 Agent Loop 简单，通过 Hook 扩展行为

pi-agent 采用了另一种思路。

它没有要求开发者将所有执行过程设计成状态图，而是以一个相对简洁的 Agent Loop 为核心，通过工具定义与生命周期 Hook 扩展行为。

例如：

- `beforeToolCall`：工具执行前检查，允许阻止调用。
- `afterToolCall`：工具执行后调整结果或决定终止。
- `toolExecution`：设置全局并行或顺序执行。
- `executionMode`：为具体工具设置执行模式。
- `onUpdate`：在工具执行过程中推送进度。

pi 的 Coding Agent 还提供 Extension API，可以监听 `tool_call`、`tool_execution_start`、`tool_execution_end` 等事件。

这些机制意味着，开发者可以把权限检查、工具输出处理、UI 事件等逻辑放入不同的 Hook，而不是全部写到工具执行函数里。

不过，pi 并不是一个自动解决所有问题的企业工作流引擎。它主要提供 Agent Loop、工具执行和扩展接口。

持久化的业务状态、跨请求幂等、复杂预算策略以及数据库一致性，仍然需要应用自己解决。

**pi-agent 的吸引力在于克制：保持核心循环简单，把复杂性留给可组合的扩展。**

### 3. Vercel AI SDK：围绕 Tool Loop、流式输出和应用集成设计

Vercel AI SDK 非常适合 JavaScript / TypeScript 生态。

它将工具调用定义、参数校验、流式生成、循环控制和 UI 集成组织为一套相对一致的 API。

在它的 Agent 抽象中，值得关注几个机制：

- `ToolLoopAgent`：管理多轮模型调用和工具执行。
- `stopWhen`：声明循环停止条件。
- `prepareStep`：动态调整每一轮的配置及可用工具。
- `repairToolCall`：尝试修复无法正常解析的工具调用。
- `toolApproval` / `needsApproval`：处理需要批准的工具操作。
- `onStepFinish`、流式输出和其他生命周期回调：用于观察执行进度与结果。

例如，对于一个电商 Agent，可以在不同步骤暴露不同的工具；用户尚未批准订单时，不允许进入最终下单操作。

Vercel AI SDK 的重点不是复杂状态图，而是让**模型调用、工具执行、流式响应和应用交互**更加统一。

它尤其适合围绕 Web UI 构建聊天型 Agent 的场景。

不过，框架的 `stopWhen` 不等于完整成本管理，UI 流不等于可靠事件日志，工具批准机制也不等于数据库权限控制。

### 4. OpenAI Agents SDK：通过 Runner、Guardrails 和 Tracing 组织执行

OpenAI Agents SDK 提供了相对完整的 Agent Runtime，包括工具执行、多 Agent Handoff、Guardrails、Sessions 和 Tracing。

开发者无需从零编写典型的 Agent Loop。

针对前面的问题，它提供几类机制：

**Guardrails**：用于验证和阻止不符合规则的输入或工具操作。Function Tool 可以配置执行前后的 Tool Guardrails。

**Tool Execution Configuration**：能够控制本地 Function Tool 的并发执行数量。

**Human-in-the-loop**：对需要批准的工具调用暂停，得到批准后继续。

**Max Turns**：限制一次 Agent 运行的最大轮次，防止无界循环。

**Tracing**：记录模型调用、工具调用及 Agent 工作流中的关键执行过程，辅助排查问题。

**Tool Error Formatting**：控制什么样的工具错误消息返回给模型。

这些能力覆盖了自研 Tool Executor 中相当一部分通用基础设施。

但它们并不能自动理解电商业务中的“只能创建一次订单”“库存必须先确认”“支付请求超时不能直接重试”。

这类正确性约束必须留在可信的业务服务中。


## 四、四个框架的设计思路有什么区别？

把四个框架放在一起，可以看到不同的侧重点。

|框架|主要设计方式|更值得关注的能力|
|---|---|---|
|LangGraph / LangChain|状态图 + Middleware + ToolNode|状态、路由、恢复、复杂工作流|
|pi-agent|简洁 Agent Loop + Hooks|轻量、透明、扩展性|
|Vercel AI SDK|Tool Loop + 类型化工具 + Streaming|Web 集成、流式交互、循环控制|
|OpenAI Agents SDK|Runner + Tools + Guardrails|工具执行、审批、追踪、多 Agent|

如果是复杂、多阶段、需要恢复的工作流，LangGraph 的图和状态模型有明显优势。

如果希望保持 Runtime 足够小、容易理解和扩展，pi-agent 的设计值得研究。

如果主要开发 TypeScript Web Agent，Vercel AI SDK 对工具调用和流式 UI 的整合很方便。

如果希望获得集成的 Agent Loop、Guardrails、Tracing 和 Handoff 能力，OpenAI Agents SDK 则减少了不少基础设施工作。

## 五、哪些问题是框架能解决的，哪些不能？

| 问题    | 框架通常能做什么                 | 仍需应用解决什么        |
| ----- | ------------------------ | --------------- |
| 输入合法性 | 参数解析、Schema 校验           | 业务字段约束          |
| 预算控制  | 最大步数、运行限制与扩展点            | 实际费用预算、搜索饱和判断   |
| 权限校验  | Guardrails、Hooks、审批      | 真实用户权限和资源隔离     |
| 调度执行  | 工具并发、执行回调、取消             | 跨操作依赖与业务事务      |
| 去重幂等  | 部分缓存或执行扩展点               | 持久化幂等键、重复下单防护   |
| 错误处理  | 错误捕获、重试和消息格式化            | 业务错误码及安全恢复      |
| 状态管理  | 会话状态、Checkpoint 或运行上下文   | 外部系统状态一致性       |
| 结果分发  | Streaming、Events、Tracing | 业务 UI、审计日志的可靠保存 |

我们可以看到，框架解决得最好的是**通用运行机制**。

而应用最难的部分，往往是业务正确性。

例如，Agent 触发 `create_order`，实际涉及数据库事务、库存扣减、支付状态和幂等操作。

这些工作并不会因为引入 LangGraph 或 OpenAI Agents SDK 而自动消失。

**Agent Runtime 可以帮助我们正确组织工具调用，但不能代替可靠的业务后端。**

## 六、回到最初的问题：为什么几百行的 Tool Executor 是个危险信号？

Tool Executor 写到几百行，代表它可能已经处理了大量真实的生产环境问题：预算管理、参数校验、上下文检查、并发限制、错误分类、缓存、状态更新和事件通知。

真正值得警惕的是：这些逻辑是否都被放在同一个控制流中，并且互相依赖。

如果答案是肯定的，那么每次增加一个功能，都需要重新理解其他功能的行为。

甚至一次看似合理的重构，也可能引入新的 Bug。

例如，将结果汇总统一放到所有工具执行结束之后，代码结构可能变清晰了，但同一批次中第二个工具却可能看不到第一个工具更新的状态。

这说明**代码结构上的解耦，不代表执行语义自动正确**。

我们在阅读 Agent 框架源码时，真正值得学习的并不是它们用了多少设计模式，而是它们如何定义责任边界：

- 模型负责决定调用什么工具。
- Schema 负责验证调用参数。
- Runtime 负责协调工具执行。
- Guardrails 或 Hooks 负责执行前后的控制。
- State 负责描述运行状态。
- Streaming 和 Tracing 负责暴露运行过程。
- 业务系统负责权限、事务和数据正确性。
    
并不是每个 Agent 都需要完整的 LangGraph，也不是每个项目都值得自研一套 Runtime。

但当你发现自己的 Tool Call 方法已经有几十个分支、十几个共享状态变量时，可能就到了重新审视技术选型的时候。

## 结语

Agent 工程最容易被低估的一点，是 Tool Calling 看起来只是“让模型调用几个函数”。

真正进入生产环境后，它涉及不可靠输入、并发调度、状态管理、成本控制、错误恢复以及现实世界的副作用。

这些问题并不是某个项目独有的，也不是简单增加几个 `if-else` 就能长期解决的。

LangGraph、pi-agent、Vercel AI SDK 和 OpenAI Agents SDK 虽然采用不同的抽象，但它们都在尝试解决一个共同的问题：

**把通用的 Agent 执行机制从具体业务逻辑中分离出来，让开发者不必反复实现同一套基础设施。**

对于开发者来说，与其一开始就追求复杂的 Agent 架构，不如先理解 Tool Calling 中究竟存在哪些独立问题，再选择合适的框架与抽象。

好的 Agent 架构，不是没有复杂性，而是让每一种复杂性都有自己的位置。
